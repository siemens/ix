## React callback types

The React wrapper now uses `unknown` instead of `any` for untyped public values:

- `closeModal`, `ModalRef.close`, and `ModalRef.dismiss` default their result
  type to `unknown`.
- `IxTreeProps.renderItem` receives `unknown`.
- `IxTreeProps.onNodeRemoved` receives `CustomEvent<unknown[]>`.

Specify generic result types where needed and narrow callback values before
accessing their properties.

## Vue modal types

The Vue wrapper now uses `unknown` instead of `any` for untyped modal close reasons:

- `closeModal` defaults its reason type to `unknown`.

Specify generic reason types where needed or narrow the reason value before accessing its properties.

## Vue 3.5 requirement

`@siemens/ix-vue` now requires Vue `^3.5.0` (Vue 3.5 or newer within the Vue 3
major version). Applications using Vue 3.2 through 3.4 are no longer supported
by this wrapper.

**Migration step:**

- Update the application's `vue` dependency to `^3.5.0` and ensure Vue-related
  tooling and libraries are compatible with Vue 3.5.

## Angular 21 requirement

`@siemens/ix-angular` now requires Angular 21.2.25 (Angular v21 LTS) or newer.
The `@angular/core` and `@angular/forms` peer dependencies are `>=21.2.25`.

**Migration steps:**

- Update your application to Angular 21.2.25 or newer, for example with
  `ng update @angular/core@21 @angular/cli@21`.
- Use TypeScript `>=5.9 <6.1` as required by Angular 21.
- Ensure all third-party Angular libraries are compatible with Angular 21.
- Review the [Angular update guide](https://angular.dev/update-guide) for
  removed or changed APIs.

The wrapper supports both zone-based and zoneless applications.

## Stencil collection optional peers

The Stencil collection has four newly optional peer dependencies:
`@floating-ui/dom`, `animejs`, `luxon`, and `@stencil/core`.
`@siemens/ix-icons` remains a required peer. Collection metadata and output
consumers must install all five packages:

```sh
pnpm add @floating-ui/dom @siemens/ix-icons @stencil/core animejs luxon
```

Use the equivalent command for npm, pnpm, or another package manager.
`@siemens/ix-icons` remains required for all `@siemens/ix` consumers. Root,
custom-elements, loader, hydrate, and framework consumers do not need to install
the other four optional peers solely for IX because those outputs bundle the
runtime libraries.

## Application switch target behavior

The application switcher now passes `noopener,noreferrer` to `window.open()`
for `_blank` and named targets such as `plant-dashboard`. Newly created tabs
have no `window.opener`, and navigation no longer sends a `Referer` header.
Applications that use the opener or referrer for inter-application
communication must adapt.

Previously, repeated selections of a named target normally reused the same
tab. With the new features, if no reusable named tab exists, repeated selections
can create separate tabs instead. Named targets are not a guarantee of either
reuse or isolation: Chromium can still reuse a named tab previously opened
without `noopener`, retaining that tab's existing opener connection.

`_self`, `_parent`, and `_top` retain their existing navigation behavior and
are opened without these features.

**Migration steps:**

- Use `_blank` when each selection must open a fresh, isolated tab.
- Use `_self`, `_parent`, or `_top` for navigation within the existing window
  or frame hierarchy.
- If your application requires one reusable tab per target or opener-based
  communication, manage that navigation in application code for trusted
  destinations rather than relying on named targets in the application switcher.

## Siemens design tokens

IX components now use SI Theme 6 system and reference tokens instead of legacy
IX `--theme-*` tokens. This is a semantic migration, not a prefix removal:
select a purpose-specific background, border, or text token for each use.
Semantic color tokens use the `--si-sys-color-*` namespace.

The mappings below use code-facing CSS custom-property names. Source hierarchy
paths have been flattened to the legacy `--theme-*` and new `--si-sys-*` syntax;
trailing `*` markers in the source mapping are metadata and are omitted here.
The existing typography and shadow examples map as follows:
`--theme-body` -> `--si-sys-typography-body` and `--theme-shadow-4` ->
`--si-sys-color-effects-shadow-4`.

Replace legacy token references according to how the value is used. For
example:

```css
/* Before */
color: var(--theme-color-std-text);

/* After */
color: var(--si-sys-color-text-primary);
```

Sass code can use the new public system-token module:

```scss
@use '@siemens/ix/scss/tokens/system' as sys;

color: #{sys.$si-sys-color-text-primary};
```

### Token value shapes

Replacement tokens are not guaranteed to have the same CSS value type as the
legacy token. `--si-sys-color-effects-shadow-*` tokens contain a complete
`box-shadow` value, including offsets, blur/spread where applicable, and color.
Assign a complete shadow token directly to `box-shadow`. Do not mechanically
substitute one where a legacy `--theme-color-shadow-*` token supplied only the
color component of a longer shadow declaration; these color tokens have no
direct replacement and require manual reconstruction or review. Likewise,
`--si-sys-typography-*` tokens contain complete `font` shorthand values, so use
them with `font`, not as a `font-family` or size fragment.

The `ix-typography` formats `label`, `label-xs`, `label-sm`, `label-lg`,
`body-xs`, `display-xs`, and `display-sm` have no SI Theme 6 system-token
equivalent and were removed. Replace label formats with the closest `body`,
`body-sm`, or `body-lg` format. For removed display formats, choose a supported
display or heading format based on the intended hierarchy.

```css
/* A complete shadow token can be replaced directly. */
/* Before */
box-shadow: var(--theme-shadow-4);

/* After */
box-shadow: var(--si-sys-color-effects-shadow-4);

/* Do not mechanically replace a legacy color component this way. */
/* Before */
box-shadow: 0 2px 4px var(--theme-color-shadow-1);

/* Incorrect */
box-shadow: 0 2px 4px var(--si-sys-color-effects-shadow-1);
```

### Removed legacy theme exports

Generated themes no longer declare the remaining 196 legacy color, chart-color,
border-shorthand, font-family, and branding tokens. This includes
`--theme-color-*`, `--theme-chart-*`, the 28 `--theme-*-bdr-*` shorthands,
`--theme-font-sans`, `--theme-font-code`, and `--theme-company-logo`.
Built-in IX styles already use system/reference tokens, so their appearance
is unchanged. Applications must migrate their own usages with the mappings
below; these legacy exports are no longer available as compatibility values.

Reconstruct border shorthands with a system border width and a semantic
border color rather than substituting a color token for a complete border.
For standalone font families, use the supported
`--si-ref-typography-font-family-*` reference tokens; system typography
tokens are complete `font` shorthands. The `--theme-company-logo` token has
no system-token successor; provide an application-owned logo instead.

The five legacy timing tokens remain available with unchanged values.

### Removed shadow utility aliases

The legacy shadow utility module `scss/utilities/_shadows.scss` and its nine
`--theme-box-shadow-*` CSS custom-property aliases have been removed.
The utilities, globals, and legacy stylesheets no longer declare these aliases.
Remove direct Sass imports of the deleted module and use the complete system
shadow tokens directly with `box-shadow`.

| Removed aliases | System replacement |
| --- | --- |
| `--theme-box-shadow-lvl-1`, `--theme-box-shadow-level-1` | `--si-sys-color-effects-shadow-1` |
| `--theme-box-shadow-lvl-2`, `--theme-box-shadow-level-2` | `--si-sys-color-effects-shadow-2` |
| `--theme-box-shadow-lvl-3`, `--theme-box-shadow-level-3` | `--si-sys-color-effects-shadow-3` |
| `--theme-box-shadow-lvl-4`, `--theme-box-shadow-level-4` | `--si-sys-color-effects-shadow-4` |
| `--theme-box-shadow-insert` | No system-token successor |

```css
/* Before */
box-shadow: var(--theme-box-shadow-level-4);

/* After */
box-shadow: var(--si-sys-color-effects-shadow-4);
```

System shadow values follow the SI Theme 6 elevation design and can render
differently from the legacy values.

The `--theme-box-shadow-insert` alias previously resolved to
`--theme-inset-shadow-1`, which has no SI Theme 6 inset-shadow successor.
Remove usages of the removed alias or provide an application-defined inset
shadow. Do not replace an inset effect with an outer elevation-shadow token.
Legacy shadow definitions, including `--theme-inset-shadow-1`, have also
been removed from generated themes.
Input-like components, shared input mixins, and legacy native inputs no longer
consume it. Decorative `box-shadow` declarations and redundant `none` resets
have been removed, including hover and focus states.
The `--ix-input--box-shadow`, `--ix-select--box-shadow`,
`--ix-chat-input--box-shadow`, and `--ix-expanding-search--box-shadow`
properties have also been removed; setting them no longer changes these
controls. No replacement is provided because input-like controls have no
decorative shadow. Keyboard-focus outlines and the browser autofill background
correction are unchanged.

### Removed common dimension and typography tokens

Generated themes no longer include legacy common variables for sizing,
spacing, container dimensions, text decoration, shadow geometry, font sizes
and weights, line heights, or letter spacing. The unused branding asset alias
and duplicated `--theme-focus--outline-offset` have also been removed.
The common theme mixin now retains only the five timing compatibility
variables.

| Removed variables | Migration |
| --- | --- |
| `--theme-size-*`, control heights, icon sizes, and input minimum width | Select purpose-specific `--si-sys-sizing-size-*` or `--si-sys-sizing-icon-*` tokens. |
| `--theme-space-*` and `--theme-input-padding-*` | Use `--si-sys-sizing-spacing-x-*` and `--si-sys-sizing-spacing-y-*` for the corresponding axes. |
| `--theme-container-size-*` | Select a suitable system sizing token or an application-defined layout width; there is no universal one-to-one mapping. |
| `--theme-ms-*`, `--theme-font-size-*`, `--theme-font-weight-*`, `--theme-line-height-*`, and `--theme-letter-spacing-*` | Use a supported `--si-sys-typography-*` role with `font`. Use reference font weights when a separate weight override is needed. Do not assign a complete typography token to `font-size`. |
| `--theme-text-decoration-*` | Use CSS `none`, `underline`, or `line-through`; no system-token replacement is provided. |
| Legacy shadow geometry variables and `--theme-shadow-1` through `--theme-shadow-4` | Use the corresponding complete `--si-sys-color-effects-shadow-*` token directly with `box-shadow`. |
| `--theme-inset-shadow-1`, inner-shadow geometry, `--theme-lightbox-blur`, and `--theme-overlay-blur` | No clean system-token replacement; remove the effect or provide an application-defined value. |
| `--theme-logo--siemens` | Use an application-provided logo asset; no system-token replacement is provided. |
| `--theme-focus--outline-offset` | Use `--si-sys-sizing-focus-ring-offset`. |

Unused legacy typography shorthands, including `--theme-body`, `--theme-h*`,
`--theme-code*`, and `--theme-text-*`, have also been removed from Classic
themes. Use the supported system typography roles instead.

The remaining chat, checkbox, and event-list token consumers have been
migrated. Default spacing and chat font sizes are preserved; compact density
now also applies to the migrated chat spacing, chat typography, and checkbox
label gap. Component-scoped `--ix-*` overrides remain supported.

### Common border, radius, and focus overrides

Built-in components, shared input mixins, legacy native-input styles, and
AG Grid theme parameters now consume system sizing tokens instead of the
common geometry variables below. These legacy declarations have been removed
from the common theme mixin.
Migrate global overrides and application styles to the matching system token,
or retain a supported component-scoped `--ix-*` override.

| Legacy variable | System replacement |
| --- | --- |
| `--theme-border-width-default` | `--si-sys-sizing-border-width-default` |
| `--theme-border-width-none` | `--si-sys-sizing-border-width-none` |
| `--theme-border-width-thick` | `--si-sys-sizing-border-width-selected` |
| `--theme-focus--border-thickness`, `--theme-focus-border-thickness` | `--si-sys-sizing-border-width-default` |
| `--theme-focus-outline-offset` | `--si-sys-sizing-focus-ring-offset` |
| `--theme-default-border-radius` | `--si-sys-sizing-border-radius-sm` |
| `--theme-small-border-radius` | `--si-sys-sizing-border-radius-xs` |
| `--theme-min-border-radius` (already unused by IX) | `--si-sys-sizing-border-radius-none` |

These replacements preserve existing widths, radii, and focus offsets in
default and compact density. Both legacy focus-border variables describe a
`0.0625rem` border, not the `0.125rem` system focus-ring width; substituting
`--si-sys-sizing-focus-ring-width` would change their appearance.

The five `--theme-*-time` variables remain in use by animation styles and the
runtime duration lookup. The current system-token catalog has no duration
successors, so these timing overrides remain supported.

### Special replacements

These two legacy tokens resolve to the CSS keyword `transparent`, not to a
system-token variable. They are also listed as investigate entries in the
source guide, but are considered resolved here and are not repeated in the
manual-review table.

| Legacy token          | Replacement   |
| --------------------- | ------------- |
| `--theme-color-0`     | `transparent` |
| `--theme-color-ghost` | `transparent` |

`--si-ref-typography-font-family-mono` instead of `--theme-font-code`.

replacing the legacy `'JetBrains Mono'` default. Override the reference token
to customize the monospace font in the reset, globals, and legacy stylesheets.

## ECharts computed CSS properties

The `getComputedCSSProperty` helper exported by `@siemens/ix-echarts` no longer

custom-property name without modification.

Pass the complete SI Theme 6 system-token name, including the leading `--`:

```ts
// Before: resolves --theme-color-primary
getComputedCSSProperty('color-primary');

// After
getComputedCSSProperty('--si-sys-color-background-accent');
```

Replace every legacy short token name with its mapped system token. Select the
appropriate background, border, or text token for conditional mappings based on
how ECharts renders the value.

## Hydration class changed to attribute

The hydration class creates issues with frameworks such as React when the DOM is updated via the framework, causing bugs such as [IX component invisibility on className update](https://github.com/siemens/ix/issues/2668).

We have migrated to using the `hydrated` attribute instead, which is also fully supported by all frameworks but removes the potential for class clashing or overwriting. 

Components are now marked as hydrated with a `hydrated` attribute instead of a `hydrated` CSS class

### Migration steps

Update any code that relies on the class marker:

- CSS/SCSS selectors: replace `.hydrated` with `[hydrated]` (e.g. `ix-button.hydrated` → `ix-button[hydrated]`).
- JavaScript/TypeScript checks: replace `element.classList.contains('hydrated')` with `element.hasAttribute('hydrated')`.
- Test assertions: replace class-based matchers (e.g. Playwright `toHaveClass(/hydrated/)`) with attribute-based ones (`toHaveAttribute('hydrated')`).

## Boolean attributes on form components

Form components (`ix-checkbox`, `ix-chat-input`, `ix-date-input`, `ix-datetime-input`, `ix-input`, `ix-number-input`, `ix-radio`, `ix-select`, `ix-slider`, `ix-textarea`, `ix-time-input`, `ix-toggle`) now follow native HTML semantics for boolean attributes: a present attribute is `true`, whatever its value. For example, `required="false"` now makes a field required and validates it, and `disabled="false"` disables it. Remove the attribute, or bind the property (e.g. `[required]="false"`, `required={false}`) instead.

## Date Time Picker - locale support

Locale support was extended to date-time values and headers, so the return value strings will now be localised.

The `from` and `to` fields on `DateChangeEvent` (emitted by `ix-date-picker`, `ix-date-dropdown`) and `from`, `to`, and `time` on `DateTimeSelectEvent` (emitted by `ix-datetime-picker`) were previously always formatted using the `en-US` locale, regardless of the `locale` prop. They now reflect the locale set on the component.

If your code reads these fields and expects locale-neutral strings, migrate to the new `isoFrom`, `isoTo`, and `isoTime` fields, which always contain ISO 8601 values independent of locale.

**Note**: If you pass a `format` string, ensure to use localized formats ([see supported formats table](https://moment.github.io/luxon/#/formatting?id=table-of-tokens)) tokens in order to ensure locale-specific rendering of the date-time values.

**New fields added to event types:**

- `DateChangeEvent`: `isoFrom?: string`, `isoTo?: string`
- `DateRangeChangeEvent`: `isoFrom?: string`, `isoTo?: string`
- `DateTimeSelectEvent`: `isoFrom?: string`, `isoTo?: string`, `isoTime?: string`

  **New props:**

- `ix-time-picker` and `ix-time-input`: `locale`, `i18nAm`, and `i18nPm`
- `ix-datetime-picker`: `i18nAm`, `i18nPm`, `i18nHourColumnHeader`, `i18nMinuteColumnHeader`, `i18nSecondColumnHeader`, and `i18nMillisecondColumnHeader`

**New methods:**

- `ix-time-picker`: `getCurrentIsoTime(): Promise<string | undefined>` — returns the current time as an ISO 8601 string, independent of the `locale` prop

**Updated `ix-date-input` locale behavior:**
The `locale` prop now explicitly affects input parsing and the values emitted via `valueChange`. Previous documentation incorrectly stated that locale does not affect returned values.

## Default icon size is 20

Omitted icon `size` on **ix-icon-button**, **ix-icon-toggle-button**, and nested icons that inherit that default now renders a **20px** glyph instead of **24px**. The control host for size `20` and `24` remains **32×32**. Size `20` is also available as an explicit public value.

Most composed components follow the same omit→20 default. A smaller set of chrome icons stay on an intentional larger or smaller size (pinned in code). Treat **Figma** as the source of truth for which slots are 16 / 20 / 24 / 32; do not use this document as a size catalog.

**ix-checkbox** and **ix-radio** control glyphs also move to **20** (hit area stays 24×24). Legacy `.ix-form-control` checkboxes align to the same outer size.

```html
<!-- Before (omit → 24px glyph) -->
<ix-icon-button icon="rocket"></ix-icon-button>

<!-- After (omit → 20px glyph) -->
<ix-icon-button icon="rocket"></ix-icon-button>

<!-- Keep the previous 24px glyph -->
<ix-icon-button icon="rocket" size="24"></ix-icon-button>
```

### Migration checklist

1. Visually review screens that relied on omitted icon `size` for a 24px glyph.
2. Set `size="24"` (or the previous explicit size) wherever the previous glyph must remain.
3. Prefer omitting `size` when the new 20px default matches the design; do not hardcode `size="20"` in product code.
4. For intended sizes on composed chrome (headers, menu, tabs, etc.), follow the current Figma specs rather than assuming every icon moved to 20.

## Date and time pickers: confirmation and selection

### New `requireConfirmation` property

`ix-date-dropdown`, `ix-date-input`, `ix-datetime-input`, `ix-date-picker` and `ix-datetime-picker` have a new `requireConfirmation` property (default `false`). When enabled:

- A selection is applied only on **Confirm**. Until then the trigger label or input value stays unchanged. The pickers and `ix-date-dropdown` still report every pick with their change event (see [Change and select events](#change-and-select-events)); the inputs emit `valueChange` and `ixChange` only on **Confirm**.
- **Cancel**, <kbd>Escape</kbd> or clicking outside the dropdown discards the pending selection. Reopening shows the last confirmed value.
- **Confirm** is disabled while the selection is incomplete (e.g. no date picked, or a range with only a start date). If there is a confirmed value, it is also disabled until the selection differs from it.

Related API:

- `i18nConfirm` and `i18nCancel` set the button labels.
- `dateCancel` (`ix-date-picker`, `ix-datetime-picker`) is emitted on Cancel.
- `ix-date-dropdown` emits the new `dateSelect` event when the user applies a changed range: on Confirm with `requireConfirmation`, otherwise when a complete range or a predefined range is picked. It is not emitted for programmatic changes (e.g. changing the value of the 'from' prop).
- `ix-datetime-input`: the default `i18nDone` changes from `'Confirm'` to `'Done'`. Set `i18n-done="Confirm"` to keep the old label.

### Change and select events

`ix-date-picker`, `ix-datetime-picker`, `ix-time-picker` and `ix-date-dropdown` use the same two kinds of events, with or without `requireConfirmation`:

| Component | Change event: every pick | Select event: applied value |
| --- | --- | --- |
| `ix-date-picker` | `dateChange` | `dateSelect` |
| `ix-datetime-picker` | `dateChange`, `timeChange` | `dateSelect` |
| `ix-time-picker` | `timeChange` | `timeSelect` |
| `ix-date-dropdown` | `dateRangeChange` | `dateSelect` |

- The change event is emitted for every pick, also for a range with only a start date and for a selection that is not confirmed yet. Use it to show intermediate values.
- When a pending selection is discarded (**Cancel**, <kbd>Escape</kbd>, clicking outside, or `ix-date-dropdown` closing with only a start date), the change event is emitted again with the restored value. `dateCancel`/`timeCancel` follow it when **Cancel** was clicked.
- The select event is emitted when the value is applied: on **Done** or **Confirm**, or without `requireConfirmation`, when a complete range or a predefined range is picked in `ix-date-dropdown`. Use it for the final value.
- Binding `from`, `to` or `time` back from the change event keeps the selection pending, so **Cancel** still restores the confirmed value.

Migration: `ix-date-dropdown` now emits `dateRangeChange` for every pick, including a start date alone, and no longer on every close. If you used it for the final range, listen to `dateSelect` instead.

### `ix-time-picker` and `ix-time-input` always require confirmation

Both always show **Cancel** and **Confirm**; they have no `requireConfirmation` property.

`ix-time-picker` API changes:

- `timeChange` is still emitted for every pick, but the time is only committed on **Confirm**, which emits `timeSelect`. If you treated `timeChange` as the final value, listen to `timeSelect` instead.
- `getCurrentTime` and `getCurrentIsoTime` return the confirmed time, not the pending selection, and `undefined` until a time is confirmed.
- **Confirm** is disabled until there's a change in time value. Without a set time, the time shown in the picker can be confirmed as it is.
- Without a set time, the time shown in the picker is reported with `timeChange` on load, as a pending selection.
- **Cancel** restores the confirmed time, reports it with `timeChange` and emits the new `timeCancel` event. Without a confirmed time, it resets the picker to the current time and reports that instead; `ix-datetime-picker` does the same.
- New `i18nCancel` property for the Cancel label.

The `--ix-time-picker-footer--gap` CSS custom property has been removed. The footer now uses the shared date and time picker footer, which keeps the same default gap.

`ix-time-input` applies the time on Confirm. Cancel, <kbd>Escape</kbd> or clicking outside discards the selection. Its new `i18nCancel` property sets the Cancel label; `i18nSelectTime` still sets the Confirm label.

### Behavior without `requireConfirmation`

- `ix-date-dropdown` no longer has a **Done** button (`i18nDone` is deprecated): picking a complete range or a predefined range applies it and closes the dropdown.
- `ix-date-dropdown` closing with only a start date picked reverts to the original range value. Because the start date was already emitted with `dateRangeChange`, `dateRangeChange` is emitted again with the reverted value. Closing without changing the range emits no events (previously `dateRangeChange` was emitted on every close). In range mode the label shows a trailing ` - ` until an end date is picked.
- `ix-datetime-input` applies every picked date or time immediately (`valueChange`) and stays open until **Done** is clicked. `ixChange` is emitted once when the picker closes, like a native `change` event, so `ix-range-field` moves to the second input only after the first picker is closed.
- **Done** and **Confirm** buttons are disabled while the value is incomplete or not valid (e.g. no 'to' value selected). If there is a confirmed value, they are also disabled until the value changes. Without a confirmed value, a complete value shown in the picker (e.g. the current time of `ix-time-picker`) can be applied as it is.

### `ix-date-picker`: `dateRangeChange` deprecated

`dateRangeChange` on `ix-date-picker` is deprecated and will be removed in 7.0.0. It is emitted together with `dateChange` in range mode, with the same payload. Listen to `dateChange` instead. `ix-date-dropdown` is not affected: `dateRangeChange` remains its change event.

```js
// Before
datePicker.addEventListener('dateRangeChange', ({ detail }) => {
  const { from, to } = detail;
});

// After
datePicker.addEventListener('dateChange', ({ detail }) => {
  const { from, to } = detail;
});
```

### `ix-datetime-picker`: `dateRangeChange` no longer bubbles

The `dateRangeChange` event of the embedded date picker used to bubble out of `ix-datetime-picker`, although it was never part of its API. It is no longer emitted. Listen to `dateChange` instead, which carries the same `from`/`to` range, or to `dateSelect` for the final selection.

## Card family: status variants, `outline`, and `clickable`

`ix-card`, `ix-action-card`, `ix-push-card`, and `ix-card-accordion` now use the shared **`StatusVariant`** set and separate chrome from status. Status colors use **SDL system tokens** (`--si-sys-color-*` / `sys.$si-sys-color-*`), not legacy names (e.g. `--theme-color-alarm`).

Affected TypeScript aliases now resolve to `StatusVariant`: `CardVariant`, `ActionCardVariant`, `PushCardVariant`, `CardAccordionVariant` (all **`@deprecated`** — prefer importing `StatusVariant` directly). Import `StatusVariant` from `@siemens/ix` instead of relying on the removed layout/status string unions.

`ix-card-accordion` still accepts a `variant` prop for compatibility, but it has **no visual effect** (status chrome lives on the parent card). Prefer omitting accordion `variant` and setting status/`outline` on the parent card.

### Status variant rename

Full `StatusVariant` set: `base`, `danger`, `warning`, `caution`, `information`, `accent`, `critical`, `success`, `neutral`.

| Before | After |
| --- | --- |
| `outline` (as variant) | `variant="base"` with outline chrome (omit `outline`, or `outline={true}`) |
| `filled` (as variant) | `variant="base" outline={false}` |
| `alarm` | `danger` |
| `info` | `information` |
| `primary` (status) | `accent` |
| `warning` | `warning` (uses the warning status; the previous warning meaning moves to `caution`) |
| `critical` | `critical` (uses the critical status; the previous critical meaning moves to `warning`) |
| — | `caution` (new) |

`success` and `neutral` are unchanged. `warning` and `critical` keep their names but now stand for different statuses, so renaming alone changes their meaning. Apply the mapping in this order so a value is not renamed twice: first `warning` → `caution`, then `critical` → `warning`, wherever the previous meaning is intended.

Default `variant` is now `"base"` (previously `"outline"` / `"filled"` depending on the component). Host class is `card-base` (previously `card-outline` / `card-filled`). CSS custom properties: the `--ix-card-outline--*` prefix becomes `--ix-card-base--*`, and the per-status `--ix-card-<status>--*` properties (e.g. `--ix-card-alarm--*`) are replaced by a single `--ix-card-status-color` that is set per status.

Example SDL tokens for card status chrome: `border-danger`, `border-warning`, `border-caution`, `border-information`, `border-accent`, `border-critical`, and related status border tokens. The top strip uses `border-width-emphasis` (4px); outline sides stay `border-3`.

### New `outline` boolean

`outline` / `filled` are no longer values of `variant`. Use the boolean **`outline`** on card, action card, push card, and card accordion. When the prop is omitted, outline chrome is used (`outline !== false`). Set `outline={false}` / `outline="false"` for filled surface chrome.

```html

<ix-card variant="filled"></ix-card>
<ix-card variant="alarm"></ix-card>

<!-- after -->
<ix-card variant="base"></ix-card>
<ix-card variant="base" outline="false"></ix-card>
<ix-card variant="danger"></ix-card>
```

Filled status (`outline="false"` + non-base variant) shows a **top color strip** (`border/{status}` at `border-width-emphasis`) instead of filling the whole surface with the status color. Outline + status keeps a neutral `border-3` frame with the same top strip. Pass the same `outline` value through to `ix-card-accordion` when it is used with a filled parent card.

### `passive` removed → `clickable`

| Component | `clickable` default |
| --- | --- |
| `ix-card` | `false` |
| `ix-action-card` | `true` when omitted (`clickable !== false`) |
| `ix-push-card` | `false` (upper region; accordion stays interactive) |

```html
<ix-card passive></ix-card>
```

## `ix-toast`: status `type` rename

`ix-toast` `type` values and the `toast.*` helpers use the shared **`StatusVariant`** names plus **`error`**. Default is **`information`** (was `info`). Prop name stays `type`. Status icons follow the Toast design (`danger` → `alarm`, `warning` → `warning` triangle, `caution` → `warning-rhomb`, `information` → `info`, `critical` → `warning-octagon`, `success` → `success`, `error` → `error`) and use **`border/*`** system colors. `error` and `danger` share the danger color and differ only in the glyph. `base`, `accent`, and `neutral` are not offered. Custom `icon` / `iconColor` stay unchanged. No compatibility aliases.

| Before | After |
| --- | --- |
| `info` (default) / `toast.info` | `information` (default) / `toast.information` |
| `warning` / `toast.warning` | `warning` / `toast.warning` (uses the warning status; the previous warning meaning moves to `caution`) |
| `success` / `toast.success` | `success` / `toast.success` |
| `error` / `toast.error` | `error` / `toast.error` |
| — | `danger` / `toast.danger` (new) |
| — | `caution` / `toast.caution` (new; previous yellow `warning` meaning) |
| — | `critical` / `toast.critical` (new) |

```ts
// before
toast.info({ message: 'Saved' });
toast.warning({ message: 'Check input' });

// after
toast.information({ message: 'Saved' });
toast.caution({ message: 'Check input' }); // previous (yellow) warning meaning
```

```html
<!-- before -->
<ix-toast type="info">…</ix-toast>

<!-- after -->
<ix-toast type="information">…</ix-toast>
```

Demo / docs sample order: Success, Information, Warning, Error, Custom icon, Danger, Caution, Critical.

### Migration checklist

1. Replace `type="info"` / `toast.info` → `information` / `toast.information`.
2. Replace `type="warning"` / `toast.warning` → `caution` / `toast.caution` where the previous yellow warning meaning is intended. Keep `warning` only where the new (orange) warning status is wanted.
3. Use `danger` / `toast.danger` for the alarm glyph; keep `error` / `toast.error` when the error glyph is intended.
4. Update TypeScript usages of the old `ToastType` literal values (`info`). Prefer `ToastType` from `@siemens/ix`.

## `ix-progress-indicator`: status rename

`ix-progress-indicator` `status` values use a subset of the shared **`StatusVariant`** names plus **`error`** and **`paused`**. Prop name stays `status`. The default is **`base`** (was `default`). The component does **not** offer `danger`, `caution`, `accent`, `critical`, or `neutral` (`error` covers the danger case). Status colors use **SDL system tokens** (`--si-sys-color-*`). Helper status icons use `border/*` colors (same as Toast) and are decorative (`aria-hidden`).

| Before | After |
| --- | --- |
| `default` (default) | `base` (default) |
| `info` | `information` |
| `success` | `success` |
| `error` | `error` |
| `warning` | `warning` (uses the warning status; the previous warning meaning would be `caution`, which is not offered) |
| `paused` | `paused` |

```html
<!-- before -->
<ix-progress-indicator status="default"></ix-progress-indicator>
<ix-progress-indicator status="info"></ix-progress-indicator>

<!-- after -->
<ix-progress-indicator status="base"></ix-progress-indicator>
<!-- or omit status; base is the default -->
<ix-progress-indicator status="information"></ix-progress-indicator>
```

An unchanged `status="warning"` now renders the new (orange) warning status. There is no `caution` status on this component.

### Custom properties

| Before | After |
| --- | --- |
| `--ix-progress-indicator-*-info--*` | `--ix-progress-indicator-*-information--*` |
| `--ix-progress-indicator-track-success--background` (previous subtle track) | still present; value is now `border/4` to match Figma (error / information / warning keep `background/*-subtle`) |

Examples of renamed custom properties: `--ix-progress-indicator-fill-info--background` → `--ix-progress-indicator-fill-information--background`, and the matching `helper-`, `helper-icon-`, `label-`, and `track-` `info` variants.

Demo / docs sample order: base, success, error, information, warning, paused.

### Migration checklist

1. Replace `status="default"` → `base` (or omit `status`).
2. Replace `status="info"` → `information`.
3. Keep `success`, `error`, `warning`, and `paused` as-is. Note that `warning` now means the new warning status.
4. Update CSS and theming that targeted `.info` / `.default` classes or `--ix-progress-indicator-*-info--*` custom properties.
5. Update TypeScript usages of the old `ProgressIndicatorStatus` literals (`default`, `info`).

## No built-in validation feedback in `novalidate` forms

Form components inside a `<form novalidate>` no longer show any built-in validation feedback. Previously, some feedback still appeared despite `novalidate` - which was itself a bug. Fixes are as follows:

- `ix-input`, `ix-number-input`, `ix-textarea`, `ix-date-input`, `ix-time-input` and `ix-datetime-input` were styled as invalid after a value change, for example when a required field was cleared.
- `ix-datetime-input` showed its "not valid" message for unparseable input. `ix-date-input` and `ix-time-input` showed theirs once another validation class such as `ix-info` was set.

`validityStateChange` is still emitted, so you can apply your own validation. The date and time inputs report unparseable input as `patternMismatch`, and `ix-datetime-input` reports it as `typeMismatch`.

If you set `ix-invalid` without `invalid-text` on unparseable input, the date and time inputs still show their built-in "not valid" message. Set `invalid-text=""` to show no message.

### Migration steps

To keep the built-in feedback, remove `novalidate` from the form.

Otherwise, set `ix-invalid` and `invalid-text` from your own validation, for example based on `validityStateChange`:

```html
<form novalidate>
  <ix-date-input id="start-date" required></ix-date-input>
</form>

<script>
  const dateInput = document.getElementById('start-date');

  dateInput.addEventListener('validityStateChange', ({ detail }) => {
    const invalid = detail.patternMismatch || detail.valueMissing;
    dateInput.classList.toggle('ix-invalid', invalid);
    dateInput.invalidText = detail.valueMissing
      ? 'Start date is required'
      : 'Enter a valid date';
  });
</script>
```

### Migration checklist

1. Every form component inside a `novalidate` form that needs an error state gets `ix-invalid` and `invalid-text` from your own validation.
2. Unparseable input in `ix-date-input`, `ix-time-input` and `ix-datetime-input` is handled by your validation.

## `ix-key-value`: divider for every label position

`ix-key-value` now shows a divider below itself for every `label-position`. Previously, only `label-position="top"` showed a divider, so standalone items with `label-position="left"` now have a divider line they did not have before.

`ix-key-value` and `ix-key-value-list` both have a new `divider` property (default `true`). Items inside `ix-key-value-list` follow the list's `divider` unless they set their own.

```html
<!-- before: no divider -->
<ix-key-value label="Label" label-position="left" value="Value"></ix-key-value>

<!-- after: keep the previous appearance -->
<ix-key-value
  label="Label"
  label-position="left"
  value="Value"
  divider="false"
></ix-key-value>
```

### Migration checklist

1. Add `divider="false"` to standalone `ix-key-value` items with `label-position="left"` that should stay without a divider.
2. Use `divider="false"` on `ix-key-value-list` instead of overriding styles. It hides the dividers of all items that don't set their own `divider`; items with `divider="true"` keep theirs.
